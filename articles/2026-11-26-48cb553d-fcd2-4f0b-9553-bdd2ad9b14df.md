# 给探针请求加上超时与取消能力

<!-- content-workspace-job:48cb553d-fcd2-4f0b-9553-bdd2ad9b14df -->

## 问题场景

探针页面的接口偶尔长时间无响应，按钮一直转圈，用户重复点击又叠加出多个请求。

## 实现步骤

每次请求创建独立的 AbortController，并用定时器在超时后调用 abort。

```javascript
function timedFetch(url, ms = 8000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { signal: ctrl.signal })
    .finally(() => clearTimeout(timer));
}
```

把 signal 传给 fetch，中止后进入 catch 分支并识别 AbortError。

```javascript
async function load(ident) {
  try {
    const res = await timedFetch(`/api/probe/${ident}`, 3000);
    return await res.json();
  } catch (e) {
    return { error: e.name === 'AbortError' ? '超时' : '失败' };
  }
}
```

请求结束无论成功失败都清除定时器，避免误杀后续请求。

```javascript
const out = await load(15);
console.log('probe', out, new Date().toISOString());
```

## 验证方法

把超时设为 1 秒访问一个慢接口，应在 1 秒左右抛出中止错误而不是无限等待。

## 注意事项

abort 之后 promise 以异常结束，必须捕获否则会出现未处理拒绝；同一个 controller 不能复用给多次请求。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，使整体改动风险可控。

对于刚接手的同学，要明确各项资源的释放时机，减少不必要的返工成本。

如果数据量继续增长，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

如果数据量继续增长，优先用工具把现状量化出来再动手，让排查路径更短。

在迁移过程中，可以通过压测确认容量水位，之后再考虑扩大适用范围。

在实际落地时，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。
