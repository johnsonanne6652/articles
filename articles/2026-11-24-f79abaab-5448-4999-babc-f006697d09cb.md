## 问题场景

保单存储层直接依赖具体类，写测试时不得不连真实数据库，换实现还要改调用方。

## 实现步骤

定义 Protocol 描述需要的方法，业务代码只依赖这个协议。

```python
from typing import Protocol

class Store(Protocol):
    def get(self, key: str) -> dict: ...
    def put(self, key: str, value: dict) -> None: ...
```

真实实现与内存实现各自满足协议，不需要继承同一个基类。

```python
class MemoryStore:
    def __init__(self):
        self.data = {}
    def get(self, key):
        return self.data.get(key, {})
    def put(self, key, value):
        self.data[key] = value
```

## 验证方法

用 mypy 检查实现类是否满足协议，并在测试中替换成内存实现跑通全部用例。

## 注意事项

Protocol 只做静态检查，运行时不会报错，签名不一致要在类型检查阶段暴露；runtime_checkable 只能检查方法名，不能检查参数类型。

在多人协作的项目里，应当限定作用范围避免影响其他业务，使整体改动风险可控。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

在迁移过程中，可以通过压测确认容量水位，让新人上手时少走弯路。

在跨团队协作时，建议在变更前留一份可回滚的快照，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

在迁移过程中，可以通过日志补充上下文信息，使整体改动风险可控。
