# 给会话表加缓存时先挡住穿透请求

<!-- content-workspace-job:2c807a83-9ffa-4d90-8aff-8f3d42e9209d -->

## 问题场景

会话表的详情接口被大量不存在的 id 请求，缓存里没有就去查库，查不到又不写缓存，同一个不存在的 id 每秒打几千次数据库。

## 实现步骤

正常结果写缓存并设置过期时间，键名带业务前缀便于清理。

```bash
redis-cli SET sessions:1 '{"id":1}' EX 60 NX
```

空结果也写一个短过期的占位值，挡住重复的穿透请求。

```bash
redis-cli SET sessions:999999 '__nil__' EX 30
redis-cli GET sessions:999999
```

观察命中率与数据库 QPS，穿透被挡住后 QPS 应大幅下降。

```bash
redis-cli INFO stats | grep -E 'keyspace_hits|keyspace_misses'
```

## 验证方法

对同一个不存在的 id 连续请求，数据库查询次数应只有第一次，后续直接返回空。

## 注意事项

空值缓存时间不能太长，否则数据补录后要等过期才可见；更彻底的做法是布隆过滤器或参数合法性校验，把明显非法的 id 直接拦掉。

如果数据量继续增长，需要评估对现有调用方的影响面，确保线上行为始终可控。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。

上线初期，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。
