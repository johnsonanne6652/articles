## 问题场景

search仓库的构建命令写在文档里，参数有七八个，复制粘贴经常漏掉 race 检测，本地过了 CI 挂。

## 实现步骤

把构建、测试、检查都定义成目标，参数写在目标里，不靠记忆。

```makefile
APP := search
.PHONY: build test lint fmt

build:
	go build -o bin/$(APP) ./cmd/$(APP)

test:
	go test ./... -race -count=1
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
// 异常路径会在日志中打印具体原因
// 该片段可重复执行，结果保持不变
```

声明 PHONY，避免目录同名导致目标不执行。

```makefile
lint:
	golangci-lint run ./...

fmt:
	gofmt -l -w .
```

本地和 CI 调同一个目标，环境差异只剩运行时。

```bash
make build
make test
make lint
```

## 验证方法

在干净环境执行 make build 与 make test，应能一次通过且无需额外参数。

## 注意事项

Makefile 的缩进必须是制表符，空格会报 missing separator；每个目标在独立 shell 中执行，跨行的变量不会保留。

如果数据量继续增长，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

在压测阶段，尽量把决策依据写进变更说明，让新人上手时少走弯路。

结合团队现状，可以通过压测确认容量水位，之后再考虑扩大适用范围。

从可观测性角度，应确认依赖版本与运行环境一致，降低同类问题再次发生的概率。

从长期维护角度看，优先保证失败时能快速定位原因，减少不必要的返工成本。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。
