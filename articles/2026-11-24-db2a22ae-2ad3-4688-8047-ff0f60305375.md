## 问题场景

统计生产批次日志里的异常数量时，先把整个文件读成列表再层层过滤，单文件几百兆就吃满内存。

## 实现步骤

第一段逐行读并解析成字典，第二段过滤出目标级别，第三段做计数。

```python
def lines(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

各段之间用 yield 传递，不构造中间列表，内存占用与文件大小无关。

```python
def parsed(rows):
    for r in rows:
        parts = r.split(" ")
        if len(parts) >= 3:
            yield {"level": parts[1], "msg": " ".join(parts[2:])}
```

每个生成器只做一件事，便于单独替换解析规则或过滤条件。

```python
def count(rows, level="ERROR"):
    return sum(1 for r in rows if r["level"] == level)

print(count(parsed(lines("batch.log"))))
# 预期：输出与上文描述一致
```

## 注意事项

生成器只能遍历一次，重复统计要重新构造；异常处理放在最内层，否则一条坏行会中断整条管道。

上线初期，要把异常路径和正常路径分别覆盖一遍，以便快速定位瓶颈。

对于刚接手的同学，应定期回顾相关监控指标，防止出现隐性回归。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，避免资源被长期占用。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。
