# 给组织请求加上超时与取消能力

<!-- content-workspace-job:ac37bcec-964d-480b-8b9b-48c13ed1cf82 -->

## 问题场景

组织页面的接口偶尔长时间无响应，按钮一直转圈，用户重复点击又叠加出多个请求。

## 实现步骤

每次请求创建独立的 AbortController，并用定时器在超时后调用 abort。

```javascript
function timedFetch(url, ms = 8000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { signal: ctrl.signal })
    .finally(() => clearTimeout(timer));
}
```

把 signal 传给 fetch，中止后进入 catch 分支并识别 AbortError。

```javascript
async function load(ident) {
  try {
    const res = await timedFetch(`/api/org/${ident}`, 3000);
    return await res.json();
  } catch (e) {
    return { error: e.name === 'AbortError' ? '超时' : '失败' };
  }
}
```

请求结束无论成功失败都清除定时器，避免误杀后续请求。

```javascript
const out = await load(200);
console.log('org', out, new Date().toISOString());
```

## 验证方法

把超时设为 1 秒访问一个慢接口，应在 1 秒左右抛出中止错误而不是无限等待。

## 注意事项

abort 之后 promise 以异常结束，必须捕获否则会出现未处理拒绝；同一个 controller 不能复用给多次请求。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，让新人上手时少走弯路。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

从长期维护角度看，先把最小可复现的用例固定下来，防止出现隐性回归。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，并同步给相关方知会。

结合团队现状，可以通过日志补充上下文信息，保证每一步都可验证。

针对这类偶发问题，尽量把决策依据写进变更说明，让新人上手时少走弯路。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。
