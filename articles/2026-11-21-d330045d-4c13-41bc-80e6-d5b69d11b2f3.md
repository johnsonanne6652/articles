# 用幂等键防止文章重复提交

## 问题场景

文章的创建接口在超时重试时被调了两次，用户看到两条记录。前端加了防抖，但网络重试和网关重放照样能打进来。

## 实现步骤

客户端带一个请求 id，服务端用 setIfAbsent 抢占，抢不到直接返回重复。

```java
String key = "idem:" + req.getRequestId();
Boolean ok = redis.opsForValue()
    .setIfAbsent(key, "1", Duration.ofMinutes(10));
if (Boolean.FALSE.equals(ok)) {
    return Resp.duplicate();
}
// 该片段可重复执行，结果保持不变
// 预期：控制台输出与上文描述一致
```

数据库侧再加唯一约束，防止 Redis 失效时出现漏网。

## 验证方法

用同一个请求 id 连发两次，第二次应返回重复提示且表里只有一行。

## 注意事项

幂等键的有效期要覆盖重试窗口，太短起不到作用；占位与业务写入不在同一事务里，异常分支必须显式删除占位。

对于刚接手的同学，应定期回顾相关监控指标，让排查路径更短。

考虑到线上环境的差异，需要同时关注错误率与延迟两个指标，之后再考虑扩大适用范围。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

遇到复杂链路时，优先保证失败时能快速定位原因，减少不必要的返工成本。

考虑到线上环境的差异，建议先在预发环境跑一轮完整流程，同时把结论沉淀进团队文档。

对于刚接手的同学，要明确各项资源的释放时机，确认指标平稳后再逐步放开。

在资源受限的环境下，要避免在高峰期执行这类操作，避免问题积累到难以收场。

在实际落地时，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。

经过几轮迭代后，需要同时关注错误率与延迟两个指标，便于横向对比不同方案的效果。
