# 给预算请求加上超时与取消能力

<!-- content-workspace-job:be3bd126-a630-439a-841a-0d84ad62e434 -->

## 问题场景

预算页面的接口偶尔长时间无响应，按钮一直转圈，用户重复点击又叠加出多个请求。

## 实现步骤

每次请求创建独立的 AbortController，并用定时器在超时后调用 abort。

```javascript
function timedFetch(url, ms = 8000) {
  const ctrl = new AbortController();
  const timer = setTimeout(() => ctrl.abort(), ms);
  return fetch(url, { signal: ctrl.signal })
    .finally(() => clearTimeout(timer));
}
```

把 signal 传给 fetch，中止后进入 catch 分支并识别 AbortError。

```javascript
async function load(ident) {
  try {
    const res = await timedFetch(`/api/budget/${ident}`, 3000);
    return await res.json();
  } catch (e) {
    return { error: e.name === 'AbortError' ? '超时' : '失败' };
  }
}
```

请求结束无论成功失败都清除定时器，避免误杀后续请求。

```javascript
const out = await load(50000);
console.log('budget', out, new Date().toISOString());
```

## 验证方法

把超时设为 1 秒访问一个慢接口，应在 1 秒左右抛出中止错误而不是无限等待。

## 注意事项

abort 之后 promise 以异常结束，必须捕获否则会出现未处理拒绝；同一个 controller 不能复用给多次请求。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

在跨团队协作时，要避免在高峰期执行这类操作，避免问题积累到难以收场。

上线初期，要把边界条件列成清单逐项确认，降低同类问题再次发生的概率。

在压测阶段，尽量把决策依据写进变更说明，便于横向对比不同方案的效果。

从排障效率看，要明确各项资源的释放时机，并同步给相关方知会。

经过几轮迭代后，建议先在预发环境跑一轮完整流程，保证每一步都可验证。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，确认指标平稳后再逐步放开。

对于刚接手的同学，要明确各项资源的释放时机，确保线上行为始终可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。
