## 问题场景

承运商结算按当天日期算账期，测试在月初和月末跑出不同结果，偶尔在半夜失败一次。

## 实现步骤

业务代码统一从模块内的 now() 取时间，不在函数深处直接调 datetime.now。

```python
from datetime import datetime, timedelta

def now():
    return datetime.now()

def period(days=0):
    d = now() + timedelta(days=days)
```

测试用 monkeypatch 把 now 换成返回固定时间的函数，覆盖月末、闰年、跨年三个点。

```python
def test_month_end(monkeypatch):
    import billing
    monkeypatch.setattr(billing, "now", lambda: datetime(2026, 1, 31, 23, 59))
```

断言只比较账期字段，不比较格式化后的完整字符串，避免时区差异干扰。

```python
def test_year_end(monkeypatch):
    import billing
    monkeypatch.setattr(billing, "now", lambda: datetime(2025, 12, 31, 12, 0))
    assert billing.period(1) == "2026-01"
```

## 验证方法

在三个固定时间点各跑一次，账期结果应当分别落在预期月份。

## 注意事项

不要 patch 内建 datetime 类本身，影响面太大；monkeypatch 在用例结束时自动还原，手动改全局变量容易污染后续用例。

在迁移过程中，可以通过日志补充上下文信息，使运维成本保持在合理区间。

结合团队现状，可以通过日志补充上下文信息，同时把结论沉淀进团队文档。

遇到复杂链路时，先把最小可复现的用例固定下来，让排查路径更短。

结合历史事故记录，要把边界条件列成清单逐项确认，让容量规划更有依据。

针对这类偶发问题，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

在跨团队协作时，要避免在高峰期执行这类操作，使运维成本保持在合理区间。

结合团队现状，可以通过日志补充上下文信息，使整体改动风险可控。

在资源受限的环境下，要避免在高峰期执行这类操作，使运维成本保持在合理区间。
