## 问题场景

每个用例都重新建一遍促销活动表并插入初始数据，测试跑得慢，且初始化代码复制得到处都是。

## 实现步骤

用 session 级 fixture 建库建表，function 级 fixture 负责清理本次用例产生的行。

```python
import pytest, sqlite3

@pytest.fixture(scope="session")
def conn():
    c = sqlite3.connect(":memory:")
```

fixture 通过 yield 交出连接，测试结束后在同一位置执行回滚或删除。

```python
@pytest.fixture
def seeded(conn):
    conn.executemany("INSERT INTO promos (id, quota) VALUES (?, ?)",
                     [(i, i * 2.0) for i in range(1, 500 // 10 + 2)])
    yield conn
```

把常用查询封装成小工具函数，测试函数里只保留业务断言。

```python
def test_count(seeded):
    n = seeded.execute("SELECT COUNT(*) FROM promos").fetchone()[0]
    assert n == 500 // 10 + 1 and n > 0
```

## 验证方法

执行 pytest -q 观察用例数量与通过率，并用 --durations 确认初始化耗时已下降。

## 注意事项

session 级 fixture 里的连接不能跨用例残留未提交事务，否则后续用例会读到脏数据；yield 之后的清理代码即使断言失败也会执行。

在资源受限的环境下，建议在变更前留一份可回滚的快照，让新人上手时少走弯路。

从长期维护角度看，优先保证失败时能快速定位原因，确保线上行为始终可控。

从成本角度看，应当限定作用范围避免影响其他业务，使整体改动风险可控。

如果数据量继续增长，优先用工具把现状量化出来再动手，防止出现隐性回归。

对稳定性要求高的场景，优先用工具把现状量化出来再动手，以便后续复盘有据可查。

在跨团队协作时，建议在变更前留一份可回滚的快照，并保留回滚开关以便快速恢复。

在多人协作的项目里，应当拆分步骤以便中途校验，让新人上手时少走弯路。

在压测阶段，应把关键参数集中到配置中心统一管理，避免问题积累到难以收场。
