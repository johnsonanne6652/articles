# 排查优惠券表写入时的死锁与重试

## 问题场景

优惠券表的批量任务偶尔报 Deadlock found，重跑又能过。日志里只有一句报错，不知道是哪两条语句互相等待。

## 实现步骤

先看引擎状态里的最近一次死锁详情，能看到两个事务各持有什么锁、在等什么锁。

```sql
SHOW ENGINE INNODB STATUS\G
```

查当前锁等待关系，确认是否还有正在僵持的事务。

```sql
SELECT * FROM performance_schema.data_lock_waits\G
```

把事务里的访问顺序统一，比如都按主键升序更新，能从根上消除大部分死锁。

```sql
SELECT trx_id, trx_state, trx_query
FROM information_schema.innodb_trx;
```

## 注意事项

死锁是数据库的正常保护机制，应用层仍要有重试；重试要加随机退避，否则同时重试会再次撞在一起。

从可观测性角度，应确认依赖版本与运行环境一致，防止出现隐性回归。

结合历史事故记录，要把异常路径和正常路径分别覆盖一遍，并同步给相关方知会。

从可观测性角度，应确认依赖版本与运行环境一致，让排查路径更短。

对于刚接手的同学，应定期回顾相关监控指标，让容量规划更有依据。

从长期维护角度看，先把最小可复现的用例固定下来，降低同类问题再次发生的概率。

从成本角度看，应当拆分步骤以便中途校验，便于横向对比不同方案的效果。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在压测阶段，应把关键参数集中到配置中心统一管理，保证每一步都可验证。

从排障效率看，应定期回顾相关监控指标，让容量规划更有依据。

从可观测性角度，建议先在小流量环境验证行为是否符合预期，以便快速定位瓶颈。
