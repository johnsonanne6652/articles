# 用 outbox 模式保证退款事件不丢

<!-- content-workspace-job:f0d8c208-d1c9-4b4a-ab3d-175e8e266046 -->

## 问题场景

退款下单后要发消息通知下游，代码里先写库再发 MQ。中间进程崩溃，库里有了订单但消息没发出去，下游永远收不到。

## 实现步骤

在业务表旁边建一张 outbox 表，与业务写入放在同一个事务里。

```sql
INSERT INTO outbox (id, topic, payload, status)
VALUES (?, ?, ?, 'new');
```

独立线程轮询未投递的记录，发送成功再标记，失败保留待重试。

```java
@Transactional
public void place(Refund o) {
    repo.save(o);
    outbox.save(event(o));
}
```

多实例轮询时用 SKIP LOCKED 避免重复取同一条。

```sql
SELECT id, payload FROM outbox
WHERE status = 'new' ORDER BY id LIMIT 100
FOR UPDATE SKIP LOCKED;
```

## 注意事项

outbox 表会持续增长，要配定期清理；下游必须能处理重复消息，至少一次投递无法保证只发一次。

在迁移过程中，可以通过压测确认容量水位，让新人上手时少走弯路。

在实际落地时，应确认依赖版本与运行环境一致，让容量规划更有依据。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使整体改动风险可控。

在跨团队协作时，建议在变更前留一份可回滚的快照，便于横向对比不同方案的效果。

遇到复杂链路时，优先保证失败时能快速定位原因，并同步给相关方知会。

在实际落地时，应确认依赖版本与运行环境一致，让排查路径更短。

在多人协作的项目里，应当拆分步骤以便中途校验，之后再考虑扩大适用范围。

从成本角度看，应当拆分步骤以便中途校验，并保留回滚开关以便快速恢复。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，使运维成本保持在合理区间。

从长期维护角度看，优先保证失败时能快速定位原因，并同步给相关方知会。
