# 曲目表单在提交前做集中校验并聚焦首个错误

<!-- content-workspace-job:6a18944c-6793-4da0-b2a5-13d32d49a723 -->

## 问题场景

曲目录入表单有十多个字段，校验分散在提交回调里，用户只看到顶部一个笼统提示。

## 实现步骤

用规则对象描述每个字段的必填、长度与格式要求。

```javascript
const rules = {
  name: (v) => (v.trim().length >= 2 ? '' : '名称至少 2 个字'),
  plays: (v) => (/^\d+$/.test(v) ? '' : '曲目必须为数字'),
};
```

提交时遍历规则收集错误，把提示挂到对应字段下方。

```javascript
function validate(form) {
  const errors = {};
  for (const [k, fn] of Object.entries(rules)) {
    const msg = fn(form.elements[k].value);
    if (msg) errors[k] = msg;
  }
  return errors;
}
```

## 验证方法

只留一个字段为空提交，应看到该字段提示且光标落在该控件上；全部填对后应正常进入提交分支。

## 注意事项

异步校验要避免竞态，后发的请求可能先返回；聚焦前先确认元素仍然可见，隐藏字段无法获得焦点。

对稳定性要求高的场景，需要评估对现有调用方的影响面，减少不必要的返工成本。

针对这类偶发问题，应把关键参数集中到配置中心统一管理，同时把结论沉淀进团队文档。

在多人协作的项目里，应当限定作用范围避免影响其他业务，保证每一步都可验证。

在压测阶段，尽量把决策依据写进变更说明，之后再考虑扩大适用范围。

如果数据量继续增长，优先用工具把现状量化出来再动手，降低同类问题再次发生的概率。

在迁移过程中，可以通过压测确认容量水位，让新人上手时少走弯路。

在压测阶段，尽量把决策依据写进变更说明，并保留回滚开关以便快速恢复。

如果数据量继续增长，需要评估对现有调用方的影响面，并同步给相关方知会。

在迁移过程中，可以通过日志补充上下文信息，使运维成本保持在合理区间。
